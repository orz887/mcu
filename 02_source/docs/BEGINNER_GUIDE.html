从会写 C 到看懂声控小鸟

这份指南从 main() 出发，带你找到每个功能在哪里、数据怎样流动，以及修改一个参数后应该观察什么。第一遍不需要看懂所有硬件配置，也不需要先学调音算法。

接线、下载软件和烧录步骤见 README。当前已完成慢速GPIO亮屏诊断，可以直接运行游戏版flappy_f103；board_selftest保留供排查采样等问题。本文描述的是程序应有的行为；电脑上的编译和测试不能代替实物验证。

1. 先找到入口，再按需要找文件

从 src/main.c 开始。它只做两件事：上电初始化一次，然后反复处理七项任务。

想知道什么 打开哪个文件 先找哪个位置
程序整体怎样运行 src/main.c main()，从上往下读
想改速度、门限、刷新时间 include/app_config.h 对应的中文注释和 APP_... 参数
声音、命令和界面怎样联系起来 src/app.c app_init()，再查七个任务函数
吹气怎样变成上跳、怎样判断碰撞 src/core.c audio_gate_update()、game_flap()、game_step()
游戏变量分别是什么意思 include/core.h AudioStats、AudioGate、Game
怎样点灯、取采样、收发串口 include/board.h 先看接口和注释，再去 src/board.c 找实现
文字和小鸟怎样画出来 src/app.c、src/display.c draw_game()、display_text()、display_poll()
串口文字怎样变成命令 src/command.c command_parse()；执行动作在 app.c 的 handle_command()
吉他音高怎样计算，选学 src/pitch.c、include/pitch.h pitch_begin()、pitch_step()

.h 文件可以看成模块的使用说明：有哪些函数、需要哪些数据。.c 文件是具体做法。读到 board_led(true) 时，先知道它会点亮状态灯，就可以继续读主流程。

几个会反复遇到的 C 写法：

  • bool 只表示是或否，值是 true、false。
  • uint16_t、uint32_t 是不存负数的整数；ADC 读数和毫秒计时分别使用它们。
  • 20U 中的 U 表示无符号整数；0.11f 中的 f 表示 float 小数。
  • Game 是把一局游戏的数据放在一起的结构体；game->bird_y 表示通过指针读取其中的小鸟高度。
  • app.c 文件开头的 static 变量由本文件保存，下一轮主循环还能继续使用，不会每轮重新清零。

2. 上电后发生什么

app_init() 先调用 board_init() 配置硬件，再准备游戏、按键、声音检测和显示，最后发送启动日志并开始安静标定。

大致阶段 程序正在做什么 实物上可以观察什么
初始化 配置时钟、GPIO、串口、SPI、定时器、ADC 和 DMA 串口出现 HELLO MCU 和状态数据
前约 200 ms 等待麦克风电路稳定，暂不统计背景音量 此时不要急着吹气
随后约 1 s 根据背景音量计算声音门限 保持安静，等待 CAL DONE
同时进行 分步骤复位、清屏和开启OLED；实际等待与SPI传输速度有关 自检版显示自检页，游戏版显示准备页
持续运行 七项任务不断轮流执行 串口可查询，采样持续，游戏按自己的节奏更新

这些时间不是串起来等完才接着工作。OLED 还在等待复位时，串口和采样任务已经可以继续运行。标定完成依赖收到音频块；没有采样时不能仅凭等够时间就认定成功。

两种固件使用同一套功能。自检版默认进入 DIAG，用内部时钟工作在 64 MHz；游戏版默认进入游戏界面，优先使用外部晶振达到 72 MHz，外部时钟启动失败时回退到内部时钟。具体采用哪一种，以 status 中的 CLK 为准。

主循环负责决定，中断负责及时记下事情

main.c 中七项任务的顺序如下：

任务 每轮检查什么
app_process_audio(now) 有新音频块吗？该关闭蜂鸣器了吗？这次声音需要上跳吗？
app_process_commands(now) 收到串口字符了吗？是否已经凑齐一行命令？
app_process_keys(now) 哪个按键已稳定按下？
app_update_game(now) 距离上一步是否已到 20 ms？
app_update_tuner(now) 调音模式是否还有少量计算要继续？
app_update_display(now) 推进初始化或发最多8字节像素，必要时画下一帧
app_update_status(now) 更新状态灯，必要时发送每秒一次的状态报告

没有新数据、没有到时间，函数就返回，让下一项继续。这是普通 C 函数依次执行，不是七个函数同时运行。

中断是硬件发来的及时通知。CPU 暂时记下事情，然后回到原来执行的位置：

TIM4 每 1 ms 中断 ──→ 毫秒数加 1 ───────────→ 主循环检查时间
DMA 完成半块数据 ──→ 记录哪半块已完成 ─────→ 主循环取数据、算音量
UART 收到一个字符 ─→ 字符放进接收队列 ────→ 主循环拼命令、执行动作

游戏碰撞判断、格式化状态文字和调音计算都放在主循环里。中断里不等用户输入，也不整屏绘图。七项任务检查完后，主循环立即从第一项重新检查；计时和采样硬件按各自的节奏持续工作。

3. 为什么看时间差，而不是到处写 delay

假设蜂鸣器需要响 60 ms。在主循环里调用 HAL_Delay(60)，会让其他任务这段时间得不到处理；即使硬件仍在采样，主循环也可能错过数据块。

本项目采用“记下开始时间，下次经过时再检查”的办法。以下是 src/app.c 中关闭蜂鸣器的实际逻辑：

if (beep_active && now - beep_started >= APP_BEEP_DURATION_MS) {
    board_buzzer(0U);
    beep_active = false;
}

例如在第 1000 ms 开始响，第 1020 ms 经过这里，时间差只有 20 ms，继续做别的事；第 1060 ms 再经过，时间差达到 60 ms，关闭蜂鸣器。

游戏同样看时间差，每20ms前进一步，所以逻辑目标是每秒更新50次。屏幕每40ms尝试提交下一帧，但必须等上一张画传完，因此实际帧率还受传输速度和变化区域大小影响。主循环、游戏步进和画面刷新有各自的节奏。 改显示间隔不会直接改变游戏速度。

计时变量用 uint32_t，约 49.7 天后会从最大值回到 0。保持使用 now - started 比较短时间间隔，计数跨过 0 时仍能计算正确；不要改成比较 now >= started + duration。

4. 麦克风读数怎样变成一次上跳

2048 附近是安静时的中心，不代表声音很大

ADC 把电压转换为 0～4095 的整数。麦克风波形既要向上变化，也要向下变化，因此模拟电路把它放在约一半电源电压附近。VDDA 约为 3.3 V 时，这个中心常在约 1.65 V，对应约 2048。

这个中心叫直流偏置。实际板子的中心可能稍有偏移，所以程序每块都先求平均值，再看采样值相对平均值的变化，而不是固定减去 2048。

例如一小段采样是：

ADC 原值：  1948   2148   1948   2148
平均值：                   2048
去掉平均：  -100   +100   -100   +100
RMS 音量：                  100

RMS 的算法是“偏差平方，求平均，再开平方”。负的偏差平方后也会贡献音量，因此波形正负摆动不会互相抵消。完全不变的 2048、2048、2048、2048 算出的 RMS 则是 0。

可以在 src/core.c 的 audio_stats_compute() 对照这三行，理解式子即可，不用另行粘贴：

float deviation = (float)adc_sample(samples[index]) - average;
squared_sum += deviation * deviation;
stats->rms = (uint16_t)sqrtf(squared_sum / (float)count);

第一、二行对每个采样执行，第三行在累加结束后执行。这里直接使用普通 float 运算。RMS 是 ADC 计数单位下的声音大小，不是分贝；PEAK 是最大的瞬时偏差；CLIP 是本块中接近 ADC 上下限的样本数量。经常接近 0 或 4095，可能说明输入被削平，需要检查声音大小和模拟前端。

每个通道每秒 8000 点，主循环一次处理 128 点音频

麦克风接 PA0，电位器接 PA1。TIM3 每 125 微秒触发一次 ADC 扫描，每次依次测这两个通道。因此是音频每秒 8000 点，电位器也每秒 8000 点。

DMA 可以理解为自动把 ADC 结果搬进数组的硬件。内存顺序是：

音频0，电位器0，音频1，电位器1，音频2，电位器2，……

循环缓冲分成前后两半。每半有 128 组结果，也就是 128 个音频值和 128 个电位器值，需要 16 ms 填满。DMA 写后半区时，主循环可以取已经写好的前半区；写到末尾后，DMA 再从头开始。

应用层通过 board_audio_read() 取得一个完整音频块，同时得到这一块的电位器平均值。它返回 false 时表示本轮没有可用的新块，上层立即返回，不拿旧数据冒充新采样。

若主循环处理太慢，LOST 会增加。程序丢弃调音的半帧数据并重新等待安静，避免把中间缺了一段的声音当成连续声音。初学时保留现有采样率和缓冲大小，先改玩法参数更容易观察效果。

超过门限还不够，还要先安静一下

threshold 是声音触发门限。以门限 100 为例，audio_gate_update() 的规则是：

  1. 音量先降到 75 或以下，并连续安静至少 50 ms，才准备接受下一次响声。
  2. RMS 达到 100 或更高，并且与上一次有效触发至少相隔 180 ms，发出一次事件。
  3. 发出事件后，要重新经过安静阶段。持续吹气不会无限连跳。

实际音量每 16 ms 更新一次，因此不会恰好在第 50 ms 判定，而是在收到满足条件的下一块时判定。上下使用不同门限，也能减少音量在门槛附近波动造成的重复动作。

收到事件后，app.c 调用 game_flap(&game)。声音算法负责判断“有没有新响声”，游戏算法负责判断“现在是否可以上跳”。

上电标定先统计背景 RMS，使用“平均背景音量 × 3 + 30”作为门限基础，再限制到默认最小 70、最大 2000。比如平均背景 RMS 为 20，计算门限约为 90。APP_DEFAULT_SOUND_THRESHOLD 的 100 是起始值，正常标定结束后会被新结果覆盖。

需要试灵敏度时，先在准备界面发送 threshold 150，再短吹一次。该命令立即采用手动门限，并关闭电位器控制、结束正在进行的标定。需要重新自动标定时发送 pot off、cal，保持安静等 CAL DONE；标定期间声控被抑制，建议先用 menu 回到准备界面。

5. 游戏其实是四种情况，加上一点移动

include/core.h 的 GameState 保存当前状态。所谓状态机，就是根据“现在是哪种情况”和“收到什么输入”决定下一步。

状态 程序做什么 怎样离开
GAME_READY，准备 显示标题，等待开始 有效声音、SW1 或 flap 开局并上跳；play 直接开新局
GAME_PLAYING，运行 移动小鸟和管道，判断碰撞与计分 pause 暂停；碰撞进入结束；menu 回到准备
GAME_PAUSED，暂停 保存坐标和速度，不移动 resume 或修好的 SW2 继续；menu 回到准备
GAME_OVER，结束 显示结束画面 有效声音、SW1 或 flap 重开并上跳；play 直接开新局

play 总是新开一局，不是继续暂停的游戏。暂停期间吹气或发 flap 不会移动小鸟。最高分在重开和回菜单时保留，断电或复位后清零。

VIEW_GAME、VIEW_DIAGNOSTIC、VIEW_TUNER 是“当前看哪个界面”；上面的四态是“游戏进行到哪一步”。进入 diag 或 tuner 会清理当前一局，之后回 menu 是准备画面；想保留这一局，应使用 pause。

小鸟为什么会落下，负数为什么能让它上跳

屏幕左上角是 (0, 0)，向右是横坐标增大，向下是纵坐标增大。因此竖直速度为正表示向下，为负表示向上。

game_step() 每 20 ms 做一次类似下面的计算；实际代码还有限速和碰撞检查：

game->bird_velocity += APP_BIRD_GRAVITY;
game->bird_y += game->bird_velocity;

速度初始为 0；默认重力为 0.11f，下一步速度变成 0.11，再下一步变成 0.22，小鸟逐渐向下。吹气时 game_flap() 将速度设成 -1.80f，小鸟先向上，随后重力让速度逐渐回到正数。

bird_y、bird_velocity 和管道的 x 都是普通 float，分别表示像素位置和每步移动量。绘图时才转成整数像素，不需要先学习特殊的数字缩放。

管道每步向左移动默认 1 像素；整根越过小鸟后加一分，移出屏幕后移到右侧继续使用。想调难度，先改管道速度或开口大小，暂时保留每步 20 ms；直接改步进间隔会同时改变所有按“每步”定义的运动速度。

本批按键为什么显示 BAD F

SW1～SW4 当前存在实际接地故障，SW5 已拆除以恢复 SWD。软件不会把接地当作连续按键操作，而是要求一个键先稳定松开至少 20 ms，之后才允许产生按下事件。

BLOCKED=F 或屏上的 BAD F 表示四个键都还没通过“先松开”检查。十六进制 F 就是四个二进制位全为 1；它不是死机提示。

修好后，SW1 负责上跳或返回游戏，SW2 暂停/继续，SW3 切换界面，SW4 标定。GPIO 始终作为上拉输入读取；软件不能解除硬件短路，当前学习流程使用串口和声音即可，按键输入验收仍需返修后进行。

6. 屏幕和串口怎样提供反馈

先画在数组里，再分小段发给 OLED

OLED 是 128×64 黑白屏，一个像素只需保存亮或灭。display.c 用 1024 字节数组保存整幅画，draw_game() 等函数只是修改这个数组。

屏幕分成8页，每页高8像素、宽128像素。正式版采用实物已能显示的GPIO模拟SPI方式：一位一位改变DIN与CLK电平，具体代码见src/oled_gpio_spi.c。GPIO等待次数越多，发送越慢；正常版24次等待已由用户确认可用，兼容版保留192次。

display_present()提交一帧后，display_poll()每轮最多发送8字节像素，完成后立刻让其他任务继续。初始化命令也分成小段，避免启动时阻塞。这里没有引入线程或复杂调度，只是把“发整页”改成“这轮发一点，下轮再接着发”。

程序还用sent_framebuffer额外保存一份已发画面，每8字节与新画面对比：相同就跳过，不同才发送。这会多使用1024字节RAM，目的是用容易理解的数组比较减少重复传输，而非节省内存。发送失败不更新这份记录，复位后必须完整重发。整张画发完前，仍不允许应用层修改这张画。

想做第一个界面修改，可以在 src/app.c 的 draw_game() 中，把准备画面的这一行标题改成：

display_text(28, 15, "HELLO", 2U);

重新编译并烧录后，发送 menu，原来的 FLAPPY 应变成 HELLO。四个参数依次是横坐标、纵坐标、文字、放大倍数。

当前字库包含英文字母、数字和常用符号，不包含汉字；代码里的中文注释不会影响屏幕字体。普通大小每个字符占 6 像素横向步距，放大两倍后占 12 像素。文字不会自动折行，超出右侧会被裁掉，从最左侧开始的普通大小文字尽量控制在 21 字符以内。

屏幕接口只发送，不回读确认。SPI_ERR=0 说明驱动没有报告发送失败，不能证明接线正确或实屏已经点亮。

把串口当作程序的观察窗口

使用 3.3 V 逻辑 USB 转串口模块，TX/RX 交叉连接并共地；主板 Type-C 只供电。接线按 README 核对。电脑终端设置 115200、8 数据位、无校验、1 停止位、无流控，每条命令最后发送换行。

先逐条发送下面三行，每行都按发送或回车：

help
diag
stream on

应看到命令说明、自检模式，以及每秒一次的状态输出。发送 stream off 可以停止周期输出；status 随时手动查询一次。

状态字段 怎样理解
STATE、CLK 当前模式/游戏状态，以及实际时钟来源和频率
ADC、RMS、PEAK、CLIP 音频平均值、有效音量、峰值偏差、接近上下限的样本数
POT、VDDA 电位器原始值及换算电压、采用的参考电压
TH 当前真正使用的声音门限，以它判断标定或旋钮是否改变了设置
BLOCKS、LOST 已采集的块数、未及时取走而跳过的块数；正常采样时前者持续增加
RX_LOST、TX_LOST 接收出错/丢字次数、因发送队列空间不足而拒绝消息的次数
BLOCKED、FAULT 哪些按键未释放，以及硬件错误标志；故障位含义见 board.h
FREQ_mHz、VALID 调音频率乘 1000 和有效标志；VALID=0 时不要使用残留的频率数字

最常用的操作集中在下面：

命令 结果或注意点
menu、play、flap 回准备、开新局、上跳
pause、resume 暂停、继续当前一局
diag、tuner 看原始数据、进入选学调音功能
cal 重新采集背景音量，约 1.2 秒保持安静
threshold 150 手动设门限，允许 1～4095；同时关闭旋钮控制和当前标定
pot on、pot off 让旋钮控制门限、停止旋钮控制；关闭后保留最后的门限
vdda 3295 将参考电压设为实测值，单位 mV，允许 2000～3600
beep 默认约 4 kHz、60 ms 的短音；调音模式拒绝此命令
mute on、mute off 关闭、开启游戏蜂鸣器音效，不会关闭麦克风声控
help、status、stream on/off 看帮助、查一次状态、开关每秒状态输出

命令不区分大小写。主循环收到一整行后才解析；非法参数、超长输入不会截短后执行。串口丢字时，程序清空尚未处理的接收数据并等待新换行：先发送一个空行，再重发完整命令。

蜂鸣器声音也会被麦克风听到。v1.0.0默认开启得分与碰撞音效，同时保留防自触发：短音响60ms，但从短音开始计算，共屏蔽声音触发300ms，之后还要重新等待安静。屏蔽期间仍然采样，只是不把音量变成上跳事件。mute on关闭自动游戏音效，mute off重新开启；调音模式禁止鸣叫。

7. 改一个地方，观察一个结果

常用参数都在 include/app_config.h。先用串口试出合适范围，再改源码默认值；每次只改一项，记下原值，重新编译、烧录并对比。

想做的实验 可编辑位置或命令 可以怎样试 预期现象
吹气更容易触发 threshold 命令 threshold 150 改为 threshold 100 较小音量也能触发，但环境噪声可能更容易误触发
提高自动标定的最低门限 APP_AUTO_THRESHOLD_MIN 70 改为 100 安静环境下标定后的 TH 至少为 100；噪声较大时可能更高
减少过密上跳 APP_SOUND_COOLDOWN_MS 180 改为 250 两次有效触发需要间隔更久

开口和管道间距有编译期检查，超出合理范围会报错。看到这类错误，先回到参数检查数值，不要删除检查语句。

需要注意三个不同的“保存”：

  • 改 app_config.h 并重新编译烧录：改变下一次上电采用的默认设置。
  • 发 threshold、pot、vdda、mute 等命令：只改变本次运行的 RAM，复位或断电后恢复默认。
  • 自动标定和旋钮控制：运行时会再改变当前门限；因此修改起始门限后，还要通过 status 的 TH 看最终生效值。

旋钮默认不控制门限。发送 pot on 后，PA1 的 0～4095 大致映射为门限 40～640；门限越大，需要的声音越大。做自动标定实验时先 pot off，否则标定完成后旋钮会继续接管门限。

修改后的检查顺序

在项目根目录、已安装 PlatformIO 和本机 GCC 的环境下执行：

pio run -e flappy_f103 -e board_selftest
python3 tools/run_tests.py

第一条为单片机构建两个版本，不会自动烧录；第二条在电脑上运行算法、命令、应用和显示测试。构建结果在 .pio/build/对应版本/ 下，firmware.bin 是烧录文件之一，使用 BIN 时起始地址为 0x08000000。

需要发布用 HEX 时，构建两个版本后执行 python3 tools/package_release.py，它会生成包含 HEX 的发布包并检查文件一致性。实际下载仍按 README 操作，烧录前核对文件版本和修改时间，避免改完代码却继续下载旧文件。

这些命令通过后，再通过实物观察验证本次修改。若有测试失败，先看失败用例是否与本次参数有关，不要为了显示“通过”直接删断言。

8. 推荐的五次学习实验

第一次：点灯，认识输出和时间

先看 D1 与 D2：D1 是电源灯，软件控制的是 PC13 上的 D2。找到 board_led()，知道 true 表示亮即可，底层已经处理了低电平点亮的接法。

只修改上一节的状态灯正常闪烁间隔，观察 D2 是否从每秒短亮改为每半秒短亮。app_update_status() 每轮都会控制它，所以不要同时在 main() 里再写一个相互覆盖的点灯逻辑。若灯快闪，先通过串口检查 FAULT 和 ADC 是否更新。

第二次：串口，认识输入和反馈

发送 help、status，再开关 stream，确认命令和输出都能走通。沿着 board_uart_read() → app_process_commands() → command_parse() → handle_command() 读一次流程。

试着发送 threshold abc，应该收到错误提示，门限不会变成错误的数值。再发合法命令并查 status，体会“解析文字”和“执行动作”为什么分开。

第三次：电位器，认识模拟量

保持 pot off，在 diag 或状态输出中缓慢转动旋钮。先只看 POT 原始值是否随转动变化，再看电压换算：

电压 mV ≈ 原始值 × VDDA_mV ÷ 4095
例如原始值 2048、VDDA 3300 mV，结果约 1650 mV。

默认 3300 mV 是名义值。要核查电压精度，测量实际 VDDA 并用 vdda 命令设置，再与仪表对比；NRST 引脚电压不是 ADC 参考电压。换算式正确不等于整板已经达到小于 5% 的实测误差。

第四次：麦克风，认识“一段数据”和事件

先回 menu，发送 pot off、cal，安静等待 CAL DONE。然后进入 diag，比较安静、短吹气、持续吹气时的 ADC、RMS、PEAK。

回到 menu 后短吹一次，应从准备画面开局并上跳；持续吹气不应一直产生新上跳。需要重复触发时，给出足够安静间隔。这个实验对应 audio_stats_compute() 和 audio_gate_update()，先掌握它们即可。

第五次：游戏，认识结构体和状态

用 play、flap、pause、resume、menu 逐项观察状态。暂停后等几秒再继续，原来的小鸟位置和速度应保留；结束后重开，本局分数清零，最高分保留到本次通电结束。

把 APP_PIPE_SPEED 改为 0.7f，重新构建并烧录，再比较通过第一根管道需要的时间。能解释“参数 → 每步位移 → 屏幕现象”之后，再阅读碰撞判断和计分逻辑。

9. 调音器是选学，放到最后

前面五次实验不依赖你看懂 pitch.c。愿意继续时，可以把调音理解为：找出波形多久重复一次，再算一秒重复多少次。

每个音频块有 128 点，累积 8 块得到 1024 点，也就是约 128 ms 的声音。算法比较原波形与延后若干采样点的波形，寻找可靠的相似位置。比如一个周期约 73 点，在每秒 8000 点的采样率下，频率约为 8000 / 73 ≈ 109.6 Hz，接近 A2 的 110 Hz。

pitch_begin() 接收一帧并检查声音是否太弱或削顶；pitch_step() 每次比较少量候选周期，后面几轮继续完成。算法中的相似度、插值和音分直接用 float 表达。音分公式在代码里就是：

return 1200.0f * log2f(frequency_hz / reference_hz);

测得频率等于标准频率时，音分为 0；高一点是正数，低一点是负数。六弦标准音依次为 E2、A2、D3、G3、B3、E4，检测范围为 65～400 Hz，适合一次拨一根弦。

先发送 tuner，等待进入，再拨弦观察。静音、削顶、噪声太大或采样断开时，程序应显示等待或无效结果，而不继续把旧频率当作当前结论。实际精度仍取决于采样时钟、输入电路、音源和环境，需要上板验证。

读到这里，回到 main.c：七项任务各自的数据从哪里来、什么时候处理、结果交给谁，应该已经能逐项对上。下一次想改功能，就从对应任务和 app_config.h 开始。
